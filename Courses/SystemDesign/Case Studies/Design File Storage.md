e.g. Dropbox

> Dropbox is a cloud-based file storage service that allows users to store and share files. It provides a secure and reliable way to store and access files from anywhere, on any device.

### Functional Requirements
1. A user can ==upload== a file from any device.
2. A user can ==download== a file from any device.
3. Users should be able to ==share== a file with other users, and view files shared with them.
4. Users can automatically ==sync== files across devices.

### Non-Functional Requirements
1. The system should be highly ==available== (prioritizing availability over consistency; it's not google docs, it's dropbox)
2. The system should support files as large as ==50GB==
3. The system should be secure and reliable. We should be able to recover files if they are lost or corrupted.
4. The system should make upload, download, and sync times as ==fast== as possible.


### Core Entities
- It seems that we have a few nouns flying around:
	- File: The raw data that users will be uploading/downloading
	- FileMetadata: The metadata associated with the file, including information like the file's name/size/mime type, and user who uploaded it.
	- User: The user of our system.

### API
- For this, again we want to be able to look at our functional requirements and back these out.

Upload a file
```
POST /files
{
	file
}
```

Download a file
```
GET /files/{file_id}
{
	file,
	filemetadata
}
```

Share a file with another user
```
POST /files/{file_id}/share
{
	userId[]
}
```

Sync file/Query for changes on the remote server
```
GET /files/{file_id}/changes?since={timestamp} -> ChangeEvent[]

Each ChangeEvent includes the fileId, type of change (created/updated/deleted) and updated metadata.

By passing a `since` timestamp, the client can fetch only the changes that have occurred since its last sync.
```

### High Level
For our high level design... again, we want to first satisfy the functional requirements, so let's move through that .

For file upload:
- The best strategy for this is to avoid the large files having to go directly through the primary server itself, so we can instead use [[Presigned URL]]s. 
- For this, the user will request to upload a file:
```
POST /files/presigned-url -> PresignedUrl
{
	FileMetadata
}
```
- The application server can create the File metadata record in our transactional database with a status of "pending"... and then get a presigned URL from [[Blob Storage|Object Storage]] and return it to the client.
- The client can then POST to that url appropriately with the actual file in the body of the request to upload the file.
- Once the file is actually uploaded, the Object Storage can send a notification to our backend using something like ==S3 Notifications==. Our backend (or a worker) can then update the file metadata in our database to an "uploaded" status.

Okay, the next requirement is that you have to be able to Download a file
- A "Good" solution is to download from blob storage
	- Again, we use [[Presigned URL]]s that allow the user to directly download the file themselves, rather than having all of those large files go through our application server.
		- User does a `GET /files/{file_id}/presigned-url`, and the primary server checks that the file exists and that the user passes Authz check that they have access to the file.
		- If they do, our server asks S3 for a presigend url for that s3 object  and returns it to the user.
		- The user then uses a `GET` with that presigned URL to download it from the blob storage directly to the client.
		- ![[Pasted image 20260621162331.png]]
- A "Great" solution is to download from [[Content Delivery Network|CDN]], when we have clients all over the world.
	- When a user requests a file, we can use the CDN (e.g. [[Amazon CloudFront|CloudFront]] in front of [[Amazon S3|S3]]) to serve the file from the server closest to the user. This is faster than serving the file from our backend or Blob Storage service.
	- For security, just like with our S3 presigned URL, we can generate a URL that the user can use to download the specific file from the CDN.

Okay, next functional requirement: Users should be able to share a file with other users, perhaps by entering the mail address of the users they want to share the file with.
- A BAD solution would be to add the list of users who have access to the file directly to the file metadata as a list column. When a user opens our site, they expect to see a list of all their files and files that have been shared with them; getting the list of their files is easy, but getting the list of files shared with them is slow with this approach: We'd need to scan the sharelist of every file.
- A GREAT solution would be to create a separate table for shares, fully normalizing the data. This involves creating a new table that maps userId to fileId, where fileId is a file shared with the given user. Then we can add an index on userId to get the fileIds that have been shared with a user, and/or an index on fileIds to get the users that a file has been shared to.  We would simply query our `SharedFiles` table.
	- The table would look like:
	- ```
	  | userId (Partition Key) | fileId (Sort Key) |
		|-------------|-------------|
		| user1       | fileId1     |
		| user1       | fileId2     |
		| user2       | fileId3     |
	  ```
	- Here, `userId` and `fileId` form a composite primary key, allowing the same user to have multiple files shared with them.

Next FR: Users can automatically sync files across devices
- At a high level, we need to make sure that files are automatically synced across different devices.
- This works by keeping a copy of a particular file on each client device (locally) and also in remote storage (e.g. the "cloud"). As such, there are two directions we need to sync in.
- ==So we need to be able to sync in two directions:==
	- Local -> Remote
	- Remote -> Local
- For Local -> Remote
	- When a user updates a file on their local machine, we need to sync these changes with teh remote server.
	- We consider the remote server to be the source of truth, so it's important that we get it consistent asap so that other devices can know about changes.
	- So we need a client-side agent that:
		- Monitors the local Dropbox folder for changes, using OS-specific file system events
		- When it detects a change, it queues the modified file for upload locally
		- It then uses our upload API to send the changes to the server along with updated metadata.
		- Conflict are resolved using a [[Last Write Wins]] strategy, meaning if two users edit the same file, the most recent edit will be the one that's saved.
- For Remote -> Local
	- Maybe each client needs to know when changes happen on the remote server so that they can pull those changes down
	- Two main approaches:
		- [[Polling]]: The client periodically asks the server if anything has changed since last sync; the server queries the DB to see if any files that this user is watched have an updatedAt timestamp newer than the last time they synced. Simple, but can be slow to detect changes and can waste bandwidth if nothing has changed.
		- [[WebSockets|WebSocket]] or [[Server-Sent Event|SSE]]: The server maintains an open connection with each client and pushes notifications when changes occur. This is more complex, but provides real-time updates.
	- For dropbox, we might use a hybrid approach where each client maintains a single WebSocket connection to the server, through which the server can push change notifications for files the user has access to.
		- Active notification: The server pushes change events through the WebSocket connection in real time as they happen, giving us near-instant sync for any file change
		- Periodic polling as a safety net, since WebSocket connections can drop, and messages can be missed.

### Low Level
- How do we support large files?
	- There are two key insights:
		- Progress Indicator: Users should be able to see the progress of their upload.
		- Resumable Updates: Users should be able to pause and resume uploads, e.g. if they lose their internet connection or close the browser.
- To address these, we can use a technique called "==chunking==" to break the file into smaller pieces and upload them one at a time.  A common mistake is to chunk the file on the server, which defeats the purpose, since we still upload the entire file at once.
- For how to handle resumable request, we need to keep track of which chunks have been uploaded, and which have not. WE can do this by saving the state of the upload in the database, specifically in our FileMetadata table:
```json
{
  "id": "123",
  "name": "file.txt",
  "size": 1000,
  "mimeType": "text/plain",
  "uploadedBy": "user1",
  "status": "uploading",
  "chunks": [
    {
      "id": "chunk1",
      "status": "uploaded"
    },
    {
      "id": "chunk2",
      "status": "uploading"
    },
    {
      "id": "chunk3",
      "status": "not-uploaded"
    }
  ]
}
```


So how do we ensure that this `chunks` field is kept in sync with the actual chunks that have been uploaded?
- Implement server-side verification of chunk uploads using ==ETags==. Since S3 event notifications don't trigger for individual multipart upload parts (only when a complete object is finalized), we need to leverage S3's multipart upload API more directly.
- Each chunk gets an ETag upon successful upload, which the client can include in the PATCH request to our backend. Our backend can then verify these ETags by calling S3's ListParts API, providing an efficient way to validate multiple chunks at once. This approach balances user experience with data integrity - we accept client updates for real-time progress tracking to provide immediate feedback, but periodically verify chunk status server-side before marking the overall file as "uploaded".
